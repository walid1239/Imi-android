# خطة اختبار مكالمات IMI على هاتفين حقيقيين

لا تعتبر المكالمات جاهزة للإطلاق قبل ملء هذا الجدول من جهازين فعليين والتحقق من الصوت والصورة في الاتجاهين. سجّل نوع ICE المختار من لوحة المطوّر (direct/relay) ولا تستنتجه من نجاح الاتصال فقط.

| الحالة | نجح/فشل | نوع الاتصال (direct/relay) | زمن الإقامة (ms) | جودة الصوت | جودة الصورة | ملاحظات |
|---|---|---|---:|---|---|---|
| Wi-Fi ↔ Wi-Fi (الشبكة المنزلية نفسها) | | | | | | |
| Wi-Fi ↔ Wi-Fi (شبكتان مختلفتان) | | | | | | |
| بيانات الهاتف ↔ Wi-Fi | | | | | | |
| بيانات الهاتف ↔ بيانات الهاتف | | | | | | |
| انقطاع Wi-Fi ثم عودته | | | | | | |
| تبديل Wi-Fi إلى بيانات أثناء المكالمة | | | | | | |
| انقطاع الإنترنت ثم إعادة الاتصال | | | | | | |
| رفض إذن الميكروفون | | | | | | |
| رفض إذن الكاميرا في مكالمة فيديو | | | | | | |

## طريقة القياس

1. استخدم هاتفين حقيقيين وحسابين مختلفين.
2. سجّل الوقت من بدء الاتصال حتى ظهور الصوت ثنائي الاتجاه.
3. سجّل RTT من WebRTC stats، ونوع المرشح المحلي/البعيد المختار.
4. قيّم الصوت والصورة عملياً: جيد / متوسط / ضعيف، وسجّل التقطيع والتأخير.
5. كرر كل حالة ثلاث مرات على الأقل وفي أوقات مختلفة.
6. أعد الاختبار مع `iceTransportPolicy=relay` في جلسة اختبار مخصصة للتحقق من Coturn.
7. لا تعتبر مكالمة relay ناجحة ما لم يظهر المرشح المختار من نوع relay فعلاً.

## قرار الحاجة إلى TURN

احسب نسبة الحالات التي فشل فيها الاتصال المباشر ونجح فيها relay. لا تتخذ قرار خدمة مدفوعة قبل نتائج الهواتف الفعلية، وتقدير حجم الاستخدام وتكلفة نقل البيانات. الاختبارات الآلية أو نجاح CI لا تثبت جودة المكالمات الحقيقية.
